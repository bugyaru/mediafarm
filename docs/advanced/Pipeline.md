# 📖 Документация по формированию и выполнению Pipeline в MediaFarm

В MediaFarm **Pipeline (конвейер обработки)** — это строго типизированная последовательность шагов (`steps`), описанная в спецификации пресета (`PresetSpec`). Выполнение pipeline делегировано сервису **Worker**, который гарантирует надежность, отслеживание прогресса, аппаратный fallback и атомарность операций.

---

## 1. Архитектура выполнения Pipeline

Жизненный цикл задачи (Job) состоит из следующих этапов:

1. **Постановка задачи**: UI/API создает запись в таблице `job` со статусом `queued`, содержащую "снапшот" спецификации пресета (`spec`), параметры (`params`) и требования к ресурсам (`requires_gpu`, `cpu_cost`).
2. **Claim (Захват)**: Worker опрашивает очередь PostgreSQL с использованием `FOR UPDATE SKIP LOCKED`. Задача назначается воркеру, если у того есть свободные слоты CPU/GPU и совпадают метки (`selector`).
3. **Инициализация контекста (`JobContext`)**:
    - Создается уникальная временная директория (`workdir`) на локальном диске воркера (scratch space).
    - Инициализируется механизм отмены (`asyncio.Event`) и троттлинга прогресса.
4. **Выполнение Pipeline**: Класс `Pipeline` последовательно вызывает обработчики (`HANDLERS`) для каждого шага из `spec.steps`.
5. **Завершение**: Статус задачи обновляется на `succeeded` или `failed`. Временные файлы очищаются.

---

## 2. Детальное описание шагов (Steps)

Каждый шаг имеет уникальный `id` и реализуется отдельной асинхронной функцией в `worker/steps.py`.

### 2.1. `acquire` (Получение исходного файла)
**Цель**: Сделать исходный медиафайл доступным для локальной обработки воркером.

**Логика работы**:
- **HTTP/HTTPS URL**: Скачивает файл через `httpx` с поддержкой заголовка `Range` для **докачки (resume)** при обрыве связи. Сохраняет во временную директорию.
- **yt-dlp**: Если `engine="ytdlp"` или URL указывает на стриминговую платформу (не прямой файл), запускает `yt-dlp` для загрузки. Поддерживает параметры `live`, `max_duration_s`, `format`.
- **Storage (S3, NFS, SMB)**: Использует `StorageRegistry` для поиска хранилища по URI. Скачивает файл через соответствующий `Backend` с поддержкой resume.
- **Режим `stream`**: Если в шаге указан `mode="stream"`, файл **не скачивается**. `ctx.input` остается URL, и последующие шаги (например, `ffmpeg`) читают поток напрямую по сети.

**Возвращает**: `{"input": <путь>, "local": <bool>, "size": <int>}`

### 2.2. `probe` (Анализ медиапотока)
**Цель**: Получить точные метаданные исходного файла для построения корректных команд кодирования.

**Логика работы**:
- Выполняет `ffprobe` на локальном файле (`ctx.input`).
- **Автоматический детект интерлейса**: Если в шаге `transcode` указано `deinterlace="auto"`, а `ffprobe` не может определить порядок полей, pipeline автоматически запускает легкий фильтр `idet` на первых 150 кадрах для принятия решения о необходимости деинтерлейсинга.
- Сохраняет результат в `ctx.info` (объект `MediaInfo`) и обновляет поле `probe` в таблице `asset`.

**Возвращает**: `{"probe": <dict>, "idet": <dict>}`

### 2.3. `transcode` (Перекодирование)
**Цель**: Преобразование видео/аудио согласно спецификации `VideoSpec` и `AudioSpec`.

**Логика работы**:
- **Движок `ffmbc`**: Если указан `engine="ffmbc"`, строятся специфичные команды для Broadcast-форматов (например, IMX 50 PAL MXF OP1a).
- **Движок `ffmpeg`**:
    - **Loudnorm (2 прохода)**: Если в `AudioSpec` указан `loudnorm="ebu_r128"`, pipeline автоматически выполняет первый проход `ffmpeg` для измерения громкости, парсит лог, и подставляет измеренные значения (`measured_i`, `measured_tp`, `measured_lra`) во второй, финальный проход кодирования.
    - **Аппаратное ускорение**: Модуль `Hardware.decide()` анализирует возможности воркера. Если указан `hwaccel="cuda"`, но кодек NVENC недоступен, выбрасывается `HWAccelError`.
    - **HW Fallback**: Если возникает `HWAccelError` и в шаге установлено `fallback_to_cpu: true`, pipeline **автоматически перезапускает этот же шаг**, принудительно устанавливая `hwaccel="cpu"` и используя `cpu_codec` (например, `libx264` вместо `h264_nvenc`). Это гарантирует выполнение задачи даже при сбоях GPU.
- **Мониторинг**: Парсит вывод `ffmpeg` для расчета реального времени (`speed`), FPS и оставшегося времени (`eta_s`).

**Возвращает**: `{"path": <путь к файлу>, "size": <int>, "engine": "ffmpeg", "hw": <bool>, "speed": <float>}`

### 2.4. `thumbnail` (Генерация превью)
**Цель**: Создание статических изображений из видео.

**Логика работы**:
- Итерируется по списку `step.at` (например, `["10%", "50%", "00:01:30"]`).
- Для каждой метки вычисляет время в секундах и запускает `ffmpeg` с фильтром `thumbnail` или `select`, сохраняя результат как `.jpg`.
- Файлы сохраняются в `ctx.workdir` и позже загружаются на шаге `publish`.

**Возвращает**: `{"paths": [<список путей к JPG>]}`

### 2.5. `verify` (Валидация результата)
**Цель**: Убедиться, что выходной файл не является "битым" перед его публикацией.

**Логика работы**:
- Запускает `ffprobe` на выходном файле.
- Проверяет массив строк `step.checks`:
    - `"has_video"` / `"has_audio"`: Наличие соответствующих потоков.
    - `"duration_delta<=1.0"`: Разница длительности с исходником не превышает 1 секунды.
    - `"size>1024"`: Файл не пустой.
    - `"height==608"`: Точная проверка разрешения (полезно для специфичных стандартов).

**Возвращает**: `{"ok": true, "checks": <результаты>}` или выбрасывает ошибку.

### 2.6. `publish` (Публикация в хранилище)
**Цель**: Атомарная загрузка результатов в целевое хранилище.

**Логика работы**:
- Определяет целевое хранилище (`storage`) и шаблон пути (`path`).
- Разрешает шаблон через `build_context` (подставляет `{yyyy}`, `{asset.stem}`, `{preset.name}` и т.д.).
- **Обработка коллизий (`on_conflict`)**:
    - `"skip"`: Если файл существует, шаг помечается как `skipped`, задача считается успешной.
    - `"overwrite"`: Файл перезаписывается.
    - `"version"`: Если файл существует, к имени добавляется суффикс `_v2`, `_v3` и т.д., пока не будет найдено свободное имя.
- Вычисляет `sha256` локального файла (если запрошено).
- Использует `Backend.upload()`, который сначала пишет во временный файл (`.mf-tmp-...`), а затем атомарно переименовывает его в целевой.
- После успешной загрузки основного файла, загружает файлы превью (из шага `thumbnail`) с суффиксом `_thumb_00.jpg`.
- Создает записи в таблице `artifact`, связывая их с `job_id`.

**Возвращает**: `{"uri": <финальный_uri>, "size": <int>, "artifacts": <количество>}`

### 2.7. `notify` (Уведомление)
**Цель**: Отправка webhook-уведомления о завершении.

**Логика работы**:
- Отправляет HTTP POST запрос на URL из `step.extra.url` или `params.notify_url`.
- Полезная нагрузка включает `job_id`, `state`, список `artifacts` (URI) и `metrics` (время выполнения, скорость).

## 3. Механизмы надежности и отказоустойчивости

### 3.1. Lease и Heartbeat (Аренда задачи)
При захвате задачи воркер получает `lease` (например, на 60 секунд).
- Фоновая задача в воркере каждые 30 секунд вызывает `heartbeat`, продлевая `lease_expires_at` в БД и обновляя `progress`.
- Если воркер "упал" или завис, другой процесс (`reaper`) найдет задачи с истекшим `lease` и вернет их в статус `queued` для повторного выполнения (с увеличенным `backoff`).
- Если UI отправляет запрос на отмену, флаг `cancel_requested` в БД становится `true`. При следующем `heartbeat` воркер видит это, устанавливает `ctx.cancel.set()` и корректно завершает процессы.

### 3.2. Взвешенный прогресс (Weighted Progress)
Для точного отображения прогресса в UI каждый шаг имеет "вес":
```python
WEIGHTS = {
    "acquire": 10, "probe": 2, "transcode": 75, 
    "thumbnail": 3, "verify": 2, "publish": 8, "notify": 1
}
```
Общий прогресс (`pct`) рассчитывается как сумма весов завершенных шагов + процент выполнения текущего шага. Это предотвращает "скачки" прогресса, когда 90% времени занимает `transcode`.

### 3.3. Scratch Space Management
Перед началом тяжелых операций (`acquire`, `transcode`) вызывается `scratch.ensure_space()`, который проверяет свободное место на диске воркера. Если места недостаточно (например, нужно 1.5x от размера исходного файла + 64 МБ), задача немедленно завершается с ошибкой `ResourceError`, не дожидаясь переполнения диска.

### 3.4. Обработка отмены (Graceful Cancellation)
На каждом шаге вызывается `ctx.check_cancel()`. Если флаг отмены установлен:
- Для `ffmpeg`/`yt-dlp`: в процесс посылается сигнал `SIGTERM` (или символ `q` в stdin для `ffmpeg`), дается `grace_period` на корректное завершение, затем `SIGKILL`.
- Для загрузок: соединение HTTP/S3 обрывается, временный `.part` файл сохраняется для будущей докачки (resume).

## 4. Передача данных между шагами (JobContext)

Состояние конвейера хранится в объекте `JobContext`, который передается во все обработчики:

| Атрибут | Описание |
|---------|----------|
| `job` | Объект `ClaimedJob` из очереди (ID, priority, params). |
| `spec` | Полный объект `PresetSpec` (снапшот на момент создания задачи). |
| `workdir` | Объект `Path` временной директории (например, `/tmp/mf/job_<uuid>`). |
| `input` | Строковый путь к локальному файлу или URL (результат `acquire`). |
| `input_local` | `True`, если файл скачан на диск воркера; `False`, если это сетевой поток. |
| `info` | Объект `MediaInfo` с результатами `ffprobe`. |
| `outputs` | Словарь, куда каждый шаг записывает свой результат (например, `outputs["transcode"]["path"]`). |
| `artifacts` | Список словарей, которые будут сохранены в таблицу `artifact` на шаге `publish`. |
| `metrics` | Агрегированные метрики (скорость кодирования, причины fallback). |

## 5. Пример полного жизненного цикла задачи (Transcode Pipeline)

1. **Пользователь** создает задачу через UI, выбирая пресет `proxy_1080p_nvenc`.
2. **UI** вычисляет `idempotency_key` и создает запись в БД `job` со статусом `queued`.
3. **Worker-1** (имеющий GPU) выполняет `claim` и получает задачу. Статус меняется на `running`, `lease` установлен на 60с.
4. **Worker-1** создает `JobContext` и директорию `/tmp/mf/job_abc123`.
5. **Шаг `acquire`**: Скачивает `s3://incoming/video.mov` в `/tmp/mf/job_abc123/input.mov`.
6. **Шаг `probe`**: Запускает `ffprobe`, определяет, что видео 4K, 50fps, interlaced.
7. **Шаг `transcode`**:
    - Строит команду `ffmpeg` с `-hwaccel cuda`, `-c:v h264_nvenc`, `-vf yadif,scale=1920:1080`.
    - Запускает процесс. Парсит вывод, обновляет `progress` (до 75%).
    - *Сбой*: Драйвер NVIDIA временно недоступен → `HWAccelError`.
    - *Fallback*: Pipeline ловит ошибку, видит `fallback_to_cpu: true`, меняет `hwaccel` на `cpu` и `codec` на `libx264`, перезапускает шаг.
8. **Шаг `thumbnail`**: Генерирует `thumb_00.jpg` на 10% длительности.
9. **Шаг `verify`**: Проверяет, что выходной MP4 имеет видео и аудио, размер > 1024 байт.
10. **Шаг `publish`**:
    - Вычисляет путь: `s3://release/2026/11/video_proxy_1080p.mp4`.
    - Загружает основной файл и превью через `S3Backend`.
    - Создает 2 записи в таблице `artifact`.
11. **Завершение**: Worker вызывает `complete`, статус задачи становится `succeeded`. Временная директория удаляется.

## 6. Расширение Pipeline (Добавление новых шагов)

Архитектура позволяет легко добавлять новые типы шагов:

1. Добавьте новый `id` в кортеж `STEP_IDS` в `mf_core/schemas.py` (например, `"watermark"`).
2. Реализуйте асинхронную функцию в `worker/steps.py`:
   ```python
   async def watermark(step: StepSpec, ctx: JobContext) -> dict[str, Any]:
       # Логика наложения водяного знака на ctx.input
       # Сохранение результата в ctx.workdir
       return {"path": str(new_file), "size": new_file.stat().st_size}
   ```
3. Зарегистрируйте обработчик в словаре `HANDLERS`:
   ```python
   HANDLERS = {
       # ...
       "watermark": watermark,
   }
   ```
4. Обновите веса в `JobContext.WEIGHTS` для корректного расчета прогресса.

## 7. Рекомендации по проектированию пресетов

1. **Всегда включайте `verify`**: Это дешевая операция, которая предотвращает публикацию битых файлов и экономит место в хранилище.
2. **Используйте `fallback_to_cpu: true`**: Для продакшн-сред это критически важно. GPU может быть занят, перегрет или иметь сбой драйвера. Fallback гарантирует завершение задачи, пусть и медленнее.
3. **Оптимизируйте `acquire`**: Для больших файлов внутри одной сети используйте `mode="stream"` (если `ffmpeg` поддерживает прямой ввод), чтобы избежать двойного потребления дискового пространства (скачивание + кодирование).
4. **Используйте `on_conflict="version"` в `publish`**: Это делает конвейер идемпотентным. Повторный запуск задачи с теми же параметрами не перезапишет существующий файл, а создаст новую версию, что безопасно для архивов.
5. **Настраивайте `cpu_cost` и `gpu_sessions`**: Указывайте реальные потребности. Если пресет использует NVENC, установите `gpu_sessions: 1`, чтобы планировщик не назначал две тяжелые задачи на одну GPU, что приведет к троттлингу или OOM.
